# GitLineage — stable hosting runbook

What survives what, and how to deploy this on a single node with a real
hostname. This is the procedure the Cloudflare Quick Tunnel deployment could not
satisfy, because the tunnel URL is ephemeral and the whole service shares a
failure domain with one developer workstation.

## The failure the previous setup had

The service ran on a developer WSL instance behind an account-less Cloudflare
Quick Tunnel. Three things make that unsuitable for opening a URL publicly:

1. The hostname is random and changes whenever the tunnel restarts.
2. There is no uptime guarantee and no supervision.
3. Killing the laptop kills the product. Everything — cache, job registry, the
   process itself — shares one failure domain.

The analysis architecture was already correct; only the hosting was not.

## Choosing a host

Requirements, in order of importance:

| Requirement | Why |
| --- | --- |
| Long-running Node process, minutes-long | A cold analysis of `grpc/grpc` measured 121–311s; `microsoft/vscode` 72s at depth 200. A serverless request model cannot host this. |
| Persistent writable storage | The artifact cache and job registry must survive restart and redeploy. |
| Git CLI available | The bounded git runner is one of the provenance signals. |
| Outbound HTTPS to `api.github.com`, `raw.githubusercontent.com`, `registry.npmjs.org`, `pypi.org` | The analyzer's allowlist. |
| Stable HTTPS hostname | `/<owner>/<repo>` must be shareable. |
| Process supervision | Restart, drain, and retryable recovery depend on it. |
| Environment/secret facility | GitHub token must not live in the image or the repo. |

A small VPS is the simplest fit. One that satisfies all of the above:

- **Hetzner Cloud** CX22 — 2 vCPU, 4 GB RAM, 40 GB disk, from about EUR 4/month.
- **DigitalOcean** basic droplet — 2 vCPU, 4 GB, 80 GB, from USD 24/month.
- **Vultr**, **Linode**, **Scaleway** — equivalent sizes, similar price.

Container platforms (Fly.io, Render, Railway) also work, provided the service is
deployed as a continuously running service and given a persistent volume. A
serverless *function* deployment is not suitable.

Sizing: the box needs roughly 1 GB per concurrent analysis plus the OS. With
`GITLINEAGE_MAX_CONCURRENT_ANALYSES=2`, 2 vCPU / 4 GB is comfortable.

## Install

```bash
# 1. service user and persistent state
sudo useradd --system --home /srv/gitlineage --shell /usr/bin/false gitlineage
sudo install -d -o gitlineage -g gitlineage -m 0750 \
  /srv/gitlineage/{cache,jobs,tmp,logs}

# 2. node (any Node >= 22.18)
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt-get install -y nodejs git ca-certificates

# 3. application, deployed at a pinned revision
sudo install -d -o gitlineage -g gitlineage -m 0755 /srv/gitlineage/app
sudo -u gitlineage git clone https://github.com/yunmin311/GitLineage.git \
  /srv/gitlineage/app
cd /srv/gitlineage/app
sudo -u gitlineage git checkout ff4af77688c4ec25b88e584ac85044a0006310a9

# 4. production client bundle
sudo -u gitlineage npm ci
sudo -u gitlineage npm run build

# 5. configuration, including the GitHub token
sudo install -o root -g gitlineage -m 0640 \
  gitlineage.env.example /srv/gitlineage/gitlineage.env
sudo $EDITOR /srv/gitlineage/gitlineage.env

# 6. supervision
sudo install -m 0644 deploy/gitlineage.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now gitlineage
sudo systemctl status gitlineage
```

Or with the container image, which needs the same three volumes:

```bash
docker build -t gitlineage:ff4af776 .
docker run -d --name gitlineage --restart unless-stopped \
  -p 127.0.0.1:8080:8080 \
  -v /srv/gitlineage/cache:/var/lib/gitlineage/cache \
  -v /srv/gitlineage/jobs:/var/lib/gitlineage/jobs \
  -v /srv/gitlineage/tmp:/tmp/gitlineage \
  --env-file /srv/gitlineage/gitlineage.env \
  gitlineage:ff4af776
```

## Deploying without losing state

The one rule: **never delete the state directories during a deploy.**

```bash
# Safe: the checkout moves, the state does not.
cd /srv/gitlineage/app
sudo -u gitlineage git fetch --all
sudo -u gitlineage git checkout <new-revision>
sudo -u gitlineage npm ci
sudo -u gitlineage npm run build
sudo systemctl restart gitlineage
```

`dist/` is regenerated by the build, so it is disposable. `/srv/gitlineage/cache`
and `/srv/gitlineage/jobs` are not, and are never touched by a deploy.

A rolling deploy that changes graph schema or analyzer version is safe by
construction: artifact paths embed the schema version, so an older artifact is
literally not found under a newer contract and is recomputed rather than served.

## What survives what

| Event | Graph artifact cache | Job registry | Behaviour |
| --- | --- | --- | --- |
| Application restart | Survives | Survives | Completed jobs stay `complete`; artifacts stay served. A job in flight is failed `interrupted_by_restart` and is retryable. |
| Host reboot | Survives (disk) | Survives (disk) | Supervisor starts the service; recovery runs at startup, not on the first request. |
| Redeploy to a new revision | Survives | Survives | Only the checkout and `dist/` are replaced. |
| Cache loss | Lost | Survives | Everything recomputes. Correct, slower. No corruption is possible: artifacts are schema-validated on read. |
| Job registry loss | Survives | Lost | Completed work is still discoverable from the artifact cache. In-flight jobs become unknown; the next request starts fresh. |

## Proxy and client IP

The application binds loopback and a TLS-terminating proxy or tunnel sits in
front. Set the trusted header **only** for the edge you actually run:

- Cloudflare (named or quick tunnel): `cf-connecting-ip`
- nginx with `proxy_set_header X-Real-IP $remote_addr;`: `x-real-ip`
- Caddy, which overwrites the header itself: `x-forwarded-for`

Leaving `GITLINEAGE_TRUSTED_PROXY_HEADER` empty makes the server use the socket
address, which cannot be forged. That is the safe default. Setting it to a header
a client can also send lets anyone rotate their apparent identity and bypass the
per-address budget.

## Attaching the domain

1. Point an `A`/`AAAA` record at the host, or add the host to a Cloudflare
   tunnel's named hostname.
2. Terminate TLS at the proxy and forward to `127.0.0.1:8080`.
3. Set `GITLINEAGE_PUBLIC_ORIGIN=https://gitlineage.example` for documentation
   and link building.
4. Validate on the platform hostname **first**; only then attach the final domain.

The route schema does not change during host replacement. `/<owner>/<repo>` is
served by the same `parseRoute`, so every existing shared link keeps working.

## Verification after any deploy

```bash
BASE=https://the-hostname

curl -fsS $BASE/healthz | jq .data.config
curl -fsS $BASE/api/contract | jq '.data.graphSchemaVersion, .data.directionContract'

# a cold repository: 202 now, artifact later
JOB=$(curl -fsS -X POST -D- -o- $BASE/api/analysis/OWNER/REPO | tee /dev/stderr >/dev/null; :)
curl -fsS $BASE/api/graph/OWNER/REPO | jq '.data.graph.graph.revision.commit'

# cache hit
curl -fsS -X POST $BASE/api/analysis/OWNER/REPO | jq '{status, cacheHit}'

# state is outside the checkout
ls -d /srv/gitlineage/{cache,jobs}
cd /srv/gitlineage/app && git status --porcelain   # must be empty
```

## Logs

Structured JSON on stdout, one line per event, captured by the journal:

| Event | Records |
| --- | --- |
| `server.started` | URL, effective configuration, persistent paths |
| `http.request` | method, path, status, duration, queue depth, running count |
| `analysis.accepted` | job id, repository, dedup key, queue depth |
| `analysis.joined` | a second client attached to a running job |
| `analysis.cacheHit` | served from the artifact cache, no work started |
| `analysis.started` / `analysis.phase` | real pipeline phases |
| `analysis.completed` | server-measured duration, resolved revision, cache hit |
| `analysis.failed` | error code, duration |
| `analysis.refused` | `analysis_rate_limited` or `analysis_overloaded` |
| `job.recovered` | a job failed as `interrupted_by_restart` |

```bash
journalctl -u gitlineage -f
journalctl -u gitlineage -o cat | jq -c 'select(.event=="analysis.completed")'
```

No credential, token or cookie is ever written to a log line: the log records
repository references, job ids, durations and public revisions only.
